# VideoActAgent：面向可控视频生成的可执行导演 Agent

## 20 分钟组会汇报文案

一句话贡献：我没有重新训练一个视频基础模型，而是在视频模型之前搭建了一层“可执行、可检查、可人工修订”的导演系统，把人物调度、摄像机规划、多视角预演和真实证据管理统一起来。

---

## 1. 研究背景与目标

**建议时间：1 分钟**

**页面短文案**

- 目标：从自然语言意图得到可控视频
- 重点控制：人物调度、摄像机运动、多视角职责
- 路线：先生成可执行 Proxy，再连接视频生成模型

**口头讲稿**

大家好，我这次汇报的项目叫 VideoActAgent。最开始的问题是：能不能让用户只描述一个故事，系统先通过代码生成一个可以检查的 Blender 预演，再把预演交给 VACE、Seedance 或 Kling 生成最终视频。

我关注的不是单纯提高画面清晰度，而是三个更难控制的问题：第一，人物在什么时候从哪里移动到哪里；第二，摄像机的位置、朝向和景别如何变化；第三，多个视角如何在同一个空间和时间线上承担不同的叙事职责。

因此，我把研究目标定义为：在视频生成模型之前增加一层可执行导演系统。它先把模糊的语言意图转成结构化轨迹和 Blender Proxy，让人真正看到运动是否正确，批准后才进入昂贵的视频生成阶段。

---

## 2. 核心问题：结构控制与生成外观纠缠

**建议时间：1.5 分钟**

**页面短文案**

- 文本很难同时表达位置、速度、朝向和镜头
- V2V 容易把 Proxy 的几何结构连同低模外观一起复制
- “生成得像”不等于“运动控制正确”

**口头讲稿**

这个问题的核心矛盾是结构控制和外观生成纠缠在一起。文本 Prompt 擅长表达语义，例如“两个人在站台相遇”，但它很难精确表达两个人在 K0 到 K4 各自的位置、谁先移动、何时交汇，以及摄像机是否需要跟随或绕行。

如果直接用 Blender Proxy 做 V2V 条件，又会出现第二个问题：Proxy 本来只想表达结构，但模型可能把低模材质、圆柱人物、诊断颜色和辅助线也理解成外观参考。旧 VACE 结果与 Proxy 的平均 SSIM 达到 0.9707，说明它不是简单的字节复制，但重绘非常弱。其原因之一是旧链路同时使用彩色诊断 Proxy 和同源首帧，形成了很强的外观锚定。

所以我认为，不能用一个输入同时承担“给人调试”和“给模型生成”两种职责。系统必须把结构预演、人工验收和最终外观生成分层，并且分别评价：前一层看控制是否正确，后一层才看真人感和视觉质量。

## 3. 最初架构及其失败

**建议时间：1.5 分钟**

**页面短文案**

```text
Prompt → Blender Proxy → VACE / Seedance / Kling → 指标
```

- Kling/Seedance 旧请求实际只发送了文本
- 旧视频只覆盖 5 秒第一段，不是完整 15 秒 Proxy
- Seed 不一致，不能得出公平因果结论

**口头讲稿**

项目最初的结构比较直接：Prompt 生成 Blender Proxy，再把结果交给 VACE、Seedance 和 Kling，最后用人物轨迹指标评分。但真实审计后发现，这条链路存在几个基础问题。

第一，旧 Kling 和 Seedance 请求实际是纯文本 T2V，没有发送 Proxy、ShotScript、关键帧或人工轨迹。因此这些结果不好，不能归因于 Proxy，因为模型根本没有看到 Proxy。

第二，旧 Blender Proxy 是 15 秒三段镜头，但 API 请求只提交了第一段 5 秒文本。生成视频约 5.04 秒并不是下载不完整，而是请求本来只覆盖第一段。

第三，Seedance 原始版和修订版的实际 Seed 不相同，Kling 的 Seed 未知，也没有公平的人工文本基线。因此我撤销了“同 Seed 公平比较”“修订 Prompt 导致退化”“已经完成整片控制”等结论，只保留真实 MP4、媒体信息和有限人工点击作为描述性证据。

这一阶段最大的收获不是某个分数，而是明确了实验合同：后端到底消费了什么、视频到底多长、人工标了几次，都必须有证据，不能根据文件名或预期来推断。

## 4. 系统如何演进

**建议时间：1.5 分钟**

**页面短文案**

```text
单向生成
→ 人工轨迹标注器
→ Proxy 人工审批闭环
→ 轨迹先行
→ Agent 三机位职责规划
→ 同步 Blender 多视角预演
```

**口头讲稿**

在发现旧链路的问题后，我没有继续扩大 API 矩阵，而是先重建上层控制流程。

第一步是做人工轨迹标注器。用户可以播放完整 Proxy，在 K0 到 K4 上修改人物、物体和摄像机轨迹，而不是只看几个孤立截图。之后增加了自动初始化、撤销、清除本次绘制、冻结前缀和中文说明，解决用户不知道从哪里开始画、画错后只能刷新页面的问题。

第二步是把流程改成轨迹先行：先批准人物和物体运动，再让 Agent 规划摄像机职责。这样摄像机服务于已经确定的动作，而不是反过来让人物去适应随机镜头。

第三步是增加三机位导演界面。DeepSeek 负责 Master、Follow、Reverse 三种高层职责；确定性编译器生成三组 K0 到 K4 摄像机状态；Blender 在共享场景中一次渲染三路同步视频。最终形成了“人工调度—Agent 规划—人工微调—真实预演—人工批准”的小闭环。

## 5. 当前端到端架构

**建议时间：1.5 分钟**

**页面短文案**

```text
故事 Prompt + ShotScript
        ↓
人物/物体轨迹 S 版本：人工编辑与批准
        ↓
DeepSeek 三机位规划 P 版本：一次调用、零重试
        ↓
确定性 K0–K4 摄像机编译 + 人工微调
        ↓
Blender 同步三机位 Proxy M 版本
        ↓
自动几何检查 + 人工批准
        ↓
未来：VACE / Seedance / Kling / 显式相机模型
```

**口头讲稿**

这是当前完整架构。输入是一段连续故事 Prompt 和对应的 ShotScript。第一阶段，用户在统一轨迹图上编辑人物和物体，保存为不可变的 S 版本，批准后才能进入下一阶段。

第二阶段，DeepSeek 根据故事、已批准轨迹和锁定边界输出严格 JSON，分配三台摄像机的角色、目标、方位、景别、运动方式、时间责任段和约束。每次只调用一次，失败不会自动重试或偷偷切模型。

第三阶段，确定性编译器把高层规划转换为三套 K0 到 K4 摄像机参数。用户还可以修改机位、焦距、高度和 Roll。Blender 一次加载同一场景，输出三个同步 MP4，以及 Depth 和 CryptoObject 结构帧。

最后，系统分别进行自动几何检查和人工批准。当前流程到批准 Proxy 为止，不会自动调用视频生成 API，因此不会在用户不知情时产生费用。

## 6. 创新一：统一人物、物体和摄像机的轨迹协议

**建议时间：2 分钟**

**页面短文案**

- 一个上层协议组织 Actor / Object / Camera
- K0–K4 同时表示时间和可编辑边界
- 屏幕归一化轨迹与 Blender 世界坐标分离
- 锁定前缀保证局部修改不破坏已批准内容

**口头讲稿**

第一个核心创新是统一轨迹协议。人物、物体和摄像机不再分别由互不兼容的 Prompt 描述，而是进入同一个具有明确时间语义的上层合同。

人物和物体使用归一化画面坐标，K0、K1、K2、K3、K4 分别描述从开始到结束的关键状态。摄像机使用三维位置、Look-at、焦距、Roll、景别和插值方式。编译器负责把画面空间中的调度映射到 Blender 世界，而不是让用户直接输入难懂的三维数值。

K 点还有第二个作用：它是可编辑边界。例如从 K2 开始修改时，K0 和 K1 被视为冻结前缀，之前已经确认的内容不能改变。这样用户可以做局部修订，而不必每次重新生成整条轨迹。

这个协议的研究价值在于，它把不同控制后端隔离开。上层仍然表达同一套人物与摄像机意图，下层可以分别接 Blender、ATI、ReCamMaster、CamTrol 或其他模型，不需要强行把多个基础模型训练成一个大模型。当前真正实现的是 Blender 编译分支；其他模型仍是候选后端。

## 7. 创新二：人工导演小闭环

**建议时间：1.5 分钟**

**页面短文案**

```text
生成 Proxy → 全视频观看 → 修改后缀轨迹 → 新版本 → 再预演
```

- 人工决定语义是否正确
- 系统负责版本、约束和证据
- 不用自动分数替代导演判断

**口头讲稿**

第二个创新是把人工导演设计成系统中的正式模块，而不是实验结束后的临时检查。

用户首先观看完整 Proxy，而不是只看固定帧；然后选择人物、物体或摄像机，在轨迹图上修改 K 点。系统自动显示初始位置，支持撤销和清除未保存绘制，并把每次保存变成新的不可变版本。

这里的关键不是让人完成所有工作，而是合理划分责任。人负责回答“故事和镜头是不是我想要的”；系统负责检查数值是否合法、时间是否同步、来源是否被篡改，并保存每一步证据。

这也解释了为什么我没有做一个完全自动的 Agent。现阶段 LLM 很难仅靠分数判断构图是否有叙事效果。让 Agent 自动循环到它自己认为满意，反而可能掩盖失败。当前小闭环保留人工终审，同时把重复的编译、渲染和绑定工作自动化。

## 8. 创新三：LLM 只负责高层三机位职责

**建议时间：1.5 分钟**

**页面短文案**

- LLM 输出：角色、目标、方位、景别、责任时间段、约束
- 编译器输出：具体位置、Look-at、焦距和关键帧
- Schema 失败即停止，不修补模型答案

**口头讲稿**

第三个创新是限制 LLM 的职责。DeepSeek 不直接生成每一帧的浮点数，也不直接操作 Blender。它只处理擅长的语义问题：哪台摄像机负责全景，哪台跟随人物 A，哪台从反侧覆盖人物 B，以及每台机位负责哪一段时间。

模型必须输出严格 JSON，包括 Master、Follow、Reverse，拍摄目标、方位、景别、运动类型、Look-at 策略、责任区间和理由。三台摄像机的责任时间必须无缝覆盖完整的 0 到 1 时间轴。

数值轨迹由确定性编译器生成。这样相同规划和相同轨迹能够得到可复现的 Blender 输入，也避免 LLM 输出跳变、不可达位置或格式错误时直接驱动渲染。

真实运行中，P1 因 DeepSeek V4 默认思考模式耗尽 4096 token，JSON 被截断。系统保留失败并零重试。之后显式关闭思考模式，P2 和带 K1 锁定边界的 P3 均成功。这个案例说明，失败证据和严格门禁本身也是 Agent 系统可靠性的一部分。

## 9. 创新四：确定性三机位编译与共享世界预演

**建议时间：1.5 分钟**

**页面短文案**

- 三台摄像机共享人物、空间和时间线
- 一次 Blender 进程输出 3 路同步 MP4
- 同时保存 Depth / CryptoObject / `.blend`
- 避免“分别生成三个看似相似但空间不一致的视频”

**口头讲稿**

第四个创新是把多视角先落实为可验证的共享三维世界，而不是直接要求生成模型独立采样三个视频。

Blender 只创建一套人物、物体和场景状态，三台摄像机在同一时间轴上观察它。这样人物在 Camera A、B、C 中的三维位置完全一致，不会出现每个视角各自生成一套动作的问题。

系统在一次 Blender 进程中输出三路同步 RGB MP4，同时保存每帧 Depth、CryptoObject、共享 `.blend` 文件和实际应用的摄像机轨迹。这些结构信息未来可以成为显式控制后端的输入或评估真值。

这里要强调：当前完成的是 Blender 层的真实多视角一致性，不是生成模型层的真人多视角一致性。后者仍需要 ReCamMaster、同步多视角生成模型或受控的逐视角生成实验验证。

## 10. 创新五：不可变审批与真实证据链

**建议时间：1.5 分钟**

**页面短文案**

```text
S：轨迹版本
P：Agent 规划版本
M：真实 Blender 迭代
```

- 请求、响应、输入、输出和审批均做 SHA-256 绑定
- 失败状态保留，不覆盖、不自动搜索好 Seed
- 自动检查与人工判断分开记录

**口头讲稿**

第五个创新是把可复现性做进工作流，而不是实验结束后再整理。

每次轨迹保存形成 S 版本，每次 Agent 规划形成 P 版本，每次 Blender 渲染形成 M 版本。审批文件记录作者、时间和输入输出 SHA-256。渲染前还会重新验证已批准规划与轨迹是否匹配，防止页面显示的是一版，后台实际渲染的是另一版。

系统采用 fail-closed 策略：DeepSeek 截断、JSON 不合法、来源哈希变化、Blender 失败或自动检查失败，都会记录真实状态并停止。它不会自动重试，不会换 Seed 搜索一个看起来更好的结果，也不会写假视频或假指标冒充通过。

自动评估只负责可计算的项目，例如同步、目标可见性、相机与人物安全距离、共享世界一致性和相邻朝向跳变。构图是否好看仍由人工判断。这个区分避免把“几何合法”误写成“电影质量已通过”。

## 11. 当前真实实验结果

**建议时间：1.5 分钟**

**页面短文案**

- 6 个不同场景完成独立 5 秒参考 Proxy
- station 完成 S3 → P3 → M3 全流程并人工批准
- M3：3 路 × 15 帧，3 FPS，960×540，5.000 秒
- 自动几何检查通过；人工构图字段仍为 `unknown`
- 本轮三机位页面没有调用 VACE/Seedance/Kling

**口头讲稿**

当前仓库中有六个不同 Prompt、ShotScript 和 Blender 环境的五秒参考 Proxy，分别是站台重逢、城市路口、森林小路、工作室、咖啡交接和仓库追逐，避免了所有实验复用同一个 Proxy。

其中 station_reunion 已完成当前新链路的完整真实运行。人物轨迹最终为 S3；三机位计划为 P3，并锁定到 K1；最终人工批准的 Blender 迭代为 M3。

M3 的 Camera A、B、C 均真实解码出 15 帧、3 FPS、5.000 秒，分辨率为 960×540，文件哈希与 job.json 和 approval.json 一致。三路时长、帧数和 FPS 相同，责任目标可见率均为 1.0，相邻视角最大方向变化为 3.302819 度，自动几何检查通过。

但 `human_composition_status` 仍然是 unknown。用户进行了 Proxy 批准，审批证据已保存，但当前审批表还没有把构图、节奏和遮挡拆成结构化人工评分。这是下一步需要补充的地方。

另外，新三机位页面没有自动调用 VACE、Seedance 或 Kling，所以这组结果证明的是上层导演与 Blender 多视角链路跑通，不证明最终真人视频已经改善。

## 12. 与相关工作的区别

**建议时间：1 分钟**

**页面短文案**

- SceneCraft：文本到 Blender 场景代码 → 借鉴规划与执行分层
- MovieAgent / Camera Artist：多 Agent 电影规划 → 简化为受约束的摄影规划器
- VideoCoCo：可执行草稿再生成 → 借鉴中性 Proxy 与双引擎思想
- CamTrol / ReCamMaster / VACE：候选低层生成后端，当前未并入 M3

**口头讲稿**

与相关工作相比，我的重点不是提出新的扩散模型，而是把几类思想组合成一个轻量、可人工使用、证据完整的导演层。

SceneCraft 将文本规划转成 Blender 可执行代码，并通过渲染反馈迭代；我借鉴了“语义规划与确定性执行分层”，但把重点放到动态人物和摄像机时间线。MovieAgent 和 Camera Artist强调多角色电影制作与电影语言；我没有复制复杂多 Agent，而是只保留一个受严格 Schema 限制的摄影规划器和人工导演门。

VideoCoCo 用 Blender 可执行草稿承载物理过程，再通过生成引擎重绘。我借鉴了 Proxy 先行和诊断/生成条件分离，但没有训练 VideoCoCo-3K，也没有在当前 M3 上运行其 OmniWeaving 编辑权重。

CamTrol、ReCamMaster 和 VACE代表三种后续低层控制方向：training-free 相机注入、单视频新机位重渲染、统一视频编辑条件。它们目前都是候选或旧链路后端，不能算已经完成的新三机位生成实验。

## 13. 当前局限性

**建议时间：1 分钟**

**页面短文案**

- 多视角一致性只在 Blender 层证明
- Proxy 低模外观仍可能污染 V2V
- LLM 规划是高层语义，不是闭环自动导演
- 当前完整三机位实验只有 station 一个场景
- 自动检查不能替代人工构图评价

**口头讲稿**

当前系统还有五个明确局限。第一，多视角一致性只在 Blender 共享世界中成立，尚未证明生成模型能保持真人身份和空间一致。第二，低模 Proxy 直接进入 V2V 时仍可能污染外观，因此真人化问题还没有解决。

第三，Agent 只做高层职责规划，失败发现和自动修订能力仍然有限；当前主要闭环依赖人工导演。第四，虽然已经有六个独立参考场景，但新的“轨迹批准—Agent 规划—三机位渲染—人工批准”完整证据目前只有 station。第五，自动指标只覆盖几何合法性，构图、叙事节奏和美感还没有结构化人工评分。

所以现阶段更准确的定位是“可执行多视角导演 Baseline”，而不是已经完成的通用多视角真人 Video Agent。

---

## 14. 下一阶段计划与总结

**建议时间：1.5 分钟**

**页面短文案**

1. 增加 M2/M3 对比、基于上一版修改和人工验收表
2. 批准 Proxy 后导出统一生成包
3. 只做小规模真实后端验证，不先开大矩阵
4. 分离人物轨迹控制与相机控制实验

**口头讲稿**

下一步我不会继续堆复杂 Agent，而是先补齐当前系统最关键的实验接口。

第一，增加基于上一版 Proxy 修改、M2/M3 同屏比较和结构化人工验收表。第二，把批准的 S、P、M 版本导出为统一生成包，但仍要求用户单独确认后才调用后端。第三，只运行最小真实对照：例如一条 clay-only VACE 编辑，或在网关能力确认后运行一条 Seedance reference-video，不直接扩展到大矩阵。第四，人物轨迹和相机控制分别评价，避免一个失败掩盖另一个模块。

总结来说，我这次完成的主要贡献，是把不可控的视频生成任务改写成一个分阶段、可执行、可观看、可修订、可追溯的导演过程。当前已经真实跑通人物轨迹、Agent 三机位规划和同步 Blender Proxy；下一阶段要验证的是，这套结构控制能否被生成模型保留，同时摆脱 Proxy 的低模外观。

# 可能的提问与回答

## Q1：创新点是不是只是“做了一个前端”？

不是。前端只是人工入口，核心是统一轨迹协议、LLM 与确定性编译器的职责分离、共享世界三机位执行，以及 S/P/M 不可变证据链。前端让这些机制能够被真实使用和验收。

## Q2：为什么一定要使用 Blender？

Blender 提供确定性、可执行的时空状态。它能明确回答人物和摄像机每一时刻在哪里，并输出深度、对象 ID 和共享场景证据。纯文本 Prompt 无法提供同等精度和可检查性。

## Q3：DeepSeek 实际控制了什么？

它只规划三台摄像机的高层职责、目标、方位、景别、运动类型、时间责任段和约束。具体三维位置、Look-at、焦距和 K0–K4 数值由确定性编译器产生，用户可以继续人工修改。

## Q4：现在是否已经实现了 Proxy 到真人视频？

旧链路运行过 VACE、Kling 和 Seedance，但当前 M3 三机位页面没有调用它们。旧 VACE 存在过度继承 Proxy 外观的问题；旧 Kling/Seedance 请求主要是 prompt-only。因此目前不能声称新的三机位 Proxy 已经成功生成真人多视角视频。

## Q5：为什么不用全自动 Agent 自己修改到通过？

自动几何指标只能判断同步、可见性和碰撞，不能可靠评价叙事构图。现阶段让 Agent 根据不完整指标自动循环，可能会优化错误目标。当前采用人工终审的小闭环，更适合形成可信 Baseline。

## Q6：真实实验如何避免 Fake 检验？

每次调用、输入、输出、视频、评估和审批都保存真实文件及 SHA-256；MP4 使用真实解码帧核验；失败不会自动重试或覆盖；自动检查和人工判断分开记录。M3 的人工构图字段仍为 unknown，没有因为用户点击批准就伪造为自动评分通过。

## Q7：下一项最关键实验是什么？

不是立即跑完整矩阵，而是选择一个已批准 Proxy，做一次受控的 Proxy-conditioned 真实生成。首先验证后端是否真正消费完整 Proxy，再分别评价人物轨迹、相机背景运动和外观去低模能力。只有小样本显示有效，才扩展到六个场景。
