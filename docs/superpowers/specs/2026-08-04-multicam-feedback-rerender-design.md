# 三机位反馈重规划与重新渲染设计

## 目标

以最小改动补齐三机位人工闭环：用户观看已渲染的三机位 Proxy 后，可以直接重新渲染，或选择全部摄像机/Camera A/Camera B/Camera C，输入自然语言修改意见，让 DeepSeek 生成一个新的摄像机方案，再批准和渲染。

本次同时恢复旧单机位标注器已有的两类可视化与编辑能力：摄像机位置轨迹和摄像机注视点轨迹。旧单机位入口保持独立可启动，不改其数据和交互。

## 最小实现原则

- 复用现有 `P` 摄像机方案版本、`M` 渲染迭代和 DeepSeek 客户端。
- 复用现有 `camera_bundle`；不新增 CameraDraft 或新的版本层。
- DeepSeek 输出受 schema 约束的结构化三机位方案，不直接生成或执行 Blender Python。
- 本地 `multicam_rig.py` 将方案确定性编译为 K0-K4 的完整摄像机参数。
- 每次反馈最多调用一次 DeepSeek，零自动重试。

## 用户流程

首次流程保持不变：

`人物/物体轨迹 S1 -> Agent 摄像机方案 P1 -> 人工批准 -> Blender Proxy M1`

用户观看 M1 后有两条路径：

1. 按当前参数重新渲染：复用 M1 实际使用的 `camera_bundle`，创建 M2，不调用 DeepSeek。
2. 按意见重新规划：选择作用范围并填写反馈，创建 P2；用户检查和批准 P2 后创建 M2。

如果用户选择单台摄像机，未选择摄像机的语义方案必须与 P1 完全一致，其实际 K0-K4 参数直接从当前 M 的 `camera_bundle` 复制，不能重新编译。任何后续人工修改仍通过渲染请求中的 `camera_bundle` 提交，并被快照到对应 M 版本。

## Agent 修改接口

新增接口：

```text
POST /api/plans/{plan_id}/revise
```

请求：

```json
{
  "scope": "camera_b",
  "feedback": "B 镜头保持原位置，并始终看向 actor_2"
}
```

`scope` 只允许 `all`、`camera_a`、`camera_b`、`camera_c`。服务端向 DeepSeek 提供已批准人物轨迹、旧摄像机方案、旧方案编译出的摄像机参数、作用范围和反馈。成功时沿用现有方式创建新的 `P` 目录、`plan.json`、`evidence.json` 和 `record.json`。

单机位修改时，服务端在发布 P2 前比较未选中摄像机的结构化 assignment；任何变化都拒绝发布。编译新方案后，只采用选中摄像机的新状态，未选中摄像机从当前 M 的真实输入逐字段复制。P2 目录附带一个 `camera_bundle.json`，供 session 展示和后续渲染使用，不新增版本类型。DeepSeek 失败、schema 非法或越权修改时保留 P1/M1，不自动重试。

## 重新渲染

结果页增加“按当前参数重新渲染”。后端从当前 M 的 `input/camera_bundle.json` 读取真实使用参数，经过现有 `_validated_camera_bundle` 校验后调用现有 `prepare_render`，创建新的 M 版本。

这样可以保证重新渲染使用的不是重新推导的数据，而是用户刚刚看到的视频所绑定的实际摄像机参数。

## 三机位编辑界面

复用旧单机位 `director_panel.html` 的交互模式，在现有三机位画布中增加：

- Camera A/B/C 标签。
- “位置”和“注视点”两个编辑模式。
- 蓝色折线和方点表示 `position.xy`。
- 绿色虚线和圆点表示 `look_at.xy`。
- K0-K4 选择。
- 位置高度、注视高度、焦距和 Roll 数值输入。

点击画布只修改当前摄像机、当前 K 和当前编辑模式。未保存的修改继续保存在前端 `camera_bundle` 中；渲染时由现有接口统一校验和快照。页面提供简短中文说明，不引入新的复杂面板。

## 状态与历史

- 创建 P2 后，P1/M1 文件保留，不覆盖旧结果。
- P2 未批准时不能渲染。
- 新 M 完成后成为当前迭代，旧 M 仍可作为来源证据读取。
- Agent 调用失败或 Blender 渲染失败均保留当前可用结果，并在页面显示真实错误。
- 结果页始终保留“重新渲染”和“按意见重新规划”，批准 M 后也不隐藏。

## 验收

- 旧单机位服务仍能独立启动并返回有效 session。
- 三机位画布同时显示位置轨迹和注视点轨迹，二者均可修改。
- 当前 M 可以零 API 调用重新渲染为新 M。
- 反馈接口一次 DeepSeek 调用生成新 P，零自动重试。
- 选择 Camera B 时，Camera A/C 的 assignment 和实际 K0-K4 参数保持逐字段一致。
- 失败不会覆盖或伪造已存在的 P/M 结果。
- 使用真实 Blender 完成至少一次三机位重渲染验证；DeepSeek 仅做一次最小真实接口验证。

## 本次不做

- 不让 DeepSeek 生成完整 Blender Python。
- 不新增复杂时间线、剪辑器或镜头切换系统。
- 不重构现有 P/M 文件布局。
- 不改动 Seedance、Kling、VACE 接口。
